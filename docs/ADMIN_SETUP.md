# Админ-панель AROMA DONNA — настройка

Админ-панель открывается по адресу `/admin`. Доступ есть только у пользователей,
для которых в Firestore существует документ `admins/{uid}`.

- Проверка в интерфейсе — `src/components/admin/AdminRoute.jsx` (удобство, а не защита).
- Настоящая защита — функция `isAdmin()` в `firestore.rules` (проверяется сервером Firebase).
- В демо-режиме (без Firebase) админ-панель недоступна.

## 1. Развернуть правила Firestore

Правила в репозитории (`firestore.rules`) **не применяются автоматически**.
Перед развёртыванием сравните их с текущими правилами в
Firebase Console → Firestore Database → Rules.

Вариант А — вручную: скопируйте содержимое `firestore.rules` в Console → **Publish**.

Вариант Б — через Firebase CLI (настройки уже есть в `firebase.json` и `.firebaserc`):

```bash
npx firebase-tools login
npx firebase-tools deploy --only firestore:rules
```

> Не запускайте `deploy --only firestore` (без `:rules`), пока `firestore.indexes.json`
> не синхронизирован с Console: сначала выполните
> `npx firebase-tools firestore:indexes > firestore.indexes.json`.

## 2. Назначить первого администратора (вручную)

1. Пользователь регистрируется на сайте обычным способом (`/register`).
2. Firebase Console → **Authentication → Users** → скопируйте его **User UID**.
3. Firebase Console → **Firestore Database → Data** → **Start collection** → ID коллекции `admins`.
4. **Document ID** — вставьте UID (именно UID, не автоматический ID!).
5. Поля (для удобства, проверка смотрит только на существование документа):
   - `email` (string) — e-mail администратора;
   - `name` (string) — имя;
   - `createdAt` (timestamp) — дата назначения.
6. **Save**. Пользователь выходит и заново входит на сайт → открывает `/admin`.

Чтобы снять права — удалите документ `admins/{uid}`.

Из браузера создать, изменить или прочитать чужой документ `admins` нельзя —
это запрещено правилами. Управление администраторами из самой панели будет сделано
позже через серверный API (Vercel Function с Firebase Admin SDK; сервисный ключ
хранится только в переменных окружения Vercel, никогда в коде клиента).

## 3. Что изменилось в правилах (этап 1)

- Администратор определяется только наличием документа `admins/{uid}`
  (функция `isAdmin()` в `firestore.rules`).
- Новая коллекция `admins/{uid}`: пользователь может прочитать (`get`) только свой документ;
  `list`, `create`, `update`, `delete` из браузера запрещены.
- `isAdmin()` пока **не даёт никаких дополнительных прав** на `users`, `orders` и `reviews`.
  Права администратора будут добавлены отдельными этапами (3–4).
- `users/{uid}` — без изменений по сравнению с опубликованными правилами:
  - читать, создавать и изменять профиль может только владелец;
  - профиль содержит только поля `name`, `email`, `createdAt` — поэтому записать себе
    роль (`role`, `isAdmin` и т.п.) невозможно;
  - `name` и `email` — строки; `createdAt` при создании ставит сервер
    (`createdAt == request.time`), при изменении его менять нельзя;
  - удаление профиля из браузера запрещено.
- `users/{uid}/orders/{orderId}` и `reviews` — без изменений.

## 4. Этап 3 — раздел «Заказы»

Страницы: `/admin/orders` (список, фильтр по статусу) и
`/admin/orders/{uid}/{orderId}` (подробности и смена статуса).

### Что изменилось в правилах

- Новое правило `match /{path=**}/orders/{orderId}` — **только чтение и только для `isAdmin()`**.
  Оно нужно для запроса `collectionGroup('orders')`, которым админка читает заказы всех покупателей.
- `users/{uid}/orders/{orderId}`:
  - `update` — только `isAdmin()` и только поля `status` и `statusUpdatedAt`;
    статус — из списка `new, confirmed, shipped, delivered, cancelled`
    (тот же список в `src/utils/orderStatus.js`, совпадение проверяет `npm test`);
    `statusUpdatedAt` ставит сервер (`serverTimestamp`). Состав, сумму, адрес и данные покупателя изменить нельзя;
  - `create` — дополнительно требуется `status == 'new'` (покупатель не может сразу создать «доставленный» заказ);
  - покупатель по-прежнему читает только свои заказы и ничего в них не меняет; `delete` запрещён всем.

### Индекс

Для сортировки по дате в запросе `collectionGroup('orders')` нужен одиночный индекс
`createdAt` (по убыванию) с областью **Collection group**. Он описан в `firestore.indexes.json`
(`fieldOverrides`). Создать его можно одним из способов:

- Firebase Console → Firestore → Indexes → **Single field** → Add exemption:
  коллекция `orders`, поле `createdAt`, включить **Descending** для **Collection group**
  (индексы для Collection не выключать);
- или `npx firebase-tools deploy --only firestore:indexes`.

Пока индекса нет, админка всё равно работает: она прочитает заказы без сортировки
и отсортирует их в браузере (в консоли будет предупреждение).

### Гостевые заказы

Заказы без входа в аккаунт в Firestore **не сохраняются** — только в `localStorage`
браузера покупателя и в сообщении Telegram. Поэтому в админке их нет.

## 5. Этап 4 — раздел «Покупатели»

Страницы: `/admin/customers` (список, поиск по имени и e-mail, сортировка) и
`/admin/customers/{uid}` (профиль, статистика и заказы покупателя со ссылками на страницу заказа).
Раздел **только для чтения**: изменить или удалить покупателя из админки нельзя.

### Что изменилось в правилах

Изменена одна строка в `match /users/{userId}`:

```
allow read: if isOwner(userId) || isAdmin();
```

- Администратор может **только читать** профили `users/{uid}` (`get` и `list`):
  этого требуют список покупателей и счётчик на «Обзоре» (`getCountFromServer`).
- `create`, `update`, `delete` профиля — без изменений: создавать и менять профиль может только владелец,
  удалять — никто. Администратор писать в `users` не может.
- Правила заказов, отзывов и `admins` не менялись.
  (Заказы одного покупателя админ читает по правилу `match /{path=**}/orders/{orderId}` из этапа 3.)
- `npm test` проверяет, что у администратора в правилах `users` есть только чтение.

### Опубликовать правила

Правило нужно опубликовать так же, как в разделе 1: скопировать `firestore.rules` в
Firebase Console → Firestore Database → Rules → **Publish**, или

```bash
npx firebase-tools deploy --only firestore:rules
```

Пока правила не опубликованы, раздел «Покупатели» покажет ошибку «Нет прав»,
а карточка «Покупатели» на «Обзоре» — прочерк. Раздел «Заказы» при этом работает как прежде.
Новых индексов не требуется: поиск и сортировка выполняются в браузере.

### Какие данные показываются

- Из профиля `users/{uid}`: имя, e-mail, дата регистрации.
- Из заказов: число заказов, сумма покупок (без отменённых), дата последнего заказа;
  в карточке покупателя — телефон из последнего заказа.
- Адреса доставки в списке покупателей не показываются — только на странице заказа.
  Полный UID в интерфейсе сокращён.
- Если у покупателя есть заказы, но нет профиля `users/{uid}` (старый аккаунт или сбой при регистрации),
  он отмечается «Нет профиля», а имя и e-mail берутся из последнего заказа.
- Гостевые заказы в Firestore не сохраняются, поэтому таких покупателей в разделе нет.

## 6. Этап 5а — каталог в Firestore

Товары переехали из файла `src/data/products.js` в коллекцию Firestore `products/{id}`.
Id документов — прежние id товаров (`rose-poudree`, `oud-royal`…), поэтому адреса `/product/{id}`,
корзины и избранное покупателей продолжают работать. Работа с товарами в админ-панели —
список, редактирование, скрытие и удаление — описана в разделе 7.

### Формат документа `products/{id}`

`id, name, brand, category, concentration, fragranceFamily, intensity, notes {top, heart, base},
rating, popularity, availability, isNew, isBestseller, description {ru, ky, en},
volumes [{ml, price}], price, image, hidden, updatedAt`

- `volumes` — цена каждого объёма хранится отдельно (у демо-каталога 30, 50 и 100 мл);
  `price` — минимальная из них («цена от», по ней работают фильтр и сортировка).
- `image` — путь к файлу в `public/images/products` или URL. Firebase Storage не используется.
- `hidden: true` — товар скрыт с витрины (обратимо). `updatedAt` ставит сервер.

### Что изменилось в правилах

Добавлен блок `match /products/{productId}` и функции проверки формата (`isValidProduct` и др.).
Правила `users`, `orders`, `reviews` и `admins` не менялись.

- **Чтение:** посетитель — только товары с `hidden == false` (запрос витрины содержит этот фильтр),
  администратор — все товары, включая скрытые.
- **Создание и изменение:** только администратор и только в строгом формате: набор полей, типы,
  списки значений (категория, концентрация, наличие…), длины строк, 1–4 объёма с целым `ml`,
  `updatedAt == request.time`, `id` в данных совпадает с id документа.
- **Удаление:** только администратор и только **скрытого** товара: правило
  `allow delete: if isAdmin() && resource.data.hidden == true` (подэтап 5c.8). Видимый товар
  (`hidden == false`), а также документ без поля `hidden` или с `hidden` не boolean Firestore удалить
  не даст — даже в обход интерфейса. Интерфейс дополнительно требует JSON-копию (см. раздел 7).

### Порядок публикации — сначала правила, потом сайт

Новый код витрины читает коллекцию `products`. Пока правила этапа 5а не опубликованы, этот запрос
отклоняется, и **каталог на сайте покажет ошибку загрузки** (резервный каталог при ошибке доступа
намеренно не подставляется, чтобы ошибка не выглядела как обычный каталог). Поэтому:

1. Опубликуйте `firestore.rules` (Firebase Console → Firestore Database → Rules → **Publish**, или
   `npx firebase-tools deploy --only firestore:rules`).
2. Только после этого публикуйте новую версию сайта.

Новых индексов не требуется: фильтр `hidden == false` использует автоматический индекс одного поля.

### Резервный каталог и импорт

- Без Firebase (демо-режим) и пока в коллекции нет видимых товаров, витрина показывает каталог
  из `src/data/products.js`. Где сейчас берётся каталог — видно на «Обзоре» и в разделе «Товары».
- Ошибка Firestore (нет прав, нет сети) показывается как ошибка с кнопкой «Повторить», а не как
  пустой или резервный каталог.
- Раздел **«Товары»** → кнопка **«Импортировать демо-каталог (24 товара)»**. Кнопка видна, только если
  сервер подтвердил, что коллекция `products` пуста. Импорт заново проверяет коллекцию и записывает
  все 24 товара одной транзакцией: если хоть один документ уже существует, ничего не записывается.
  Повторный импорт поэтому не создаёт дубликатов и не перезаписывает изменённые товары.
- Если в коллекции не останется ни одного видимого товара, витрина снова покажет резервный каталог
  (посетитель не может отличить «все скрыты» от «коллекция пуста»). Поэтому админ-панель не даёт
  скрыть или удалить товар, если после этого витрина опустеет (см. раздел 7).

## 7. Товары: видимость на витрине и удаление

Раздел **«Товары»** показывает все документы коллекции `products`, включая скрытые и повреждённые.
Любое изменение видимости или удаление выполняется транзакцией и проверяет, что товар не изменили
в другой вкладке или другим администратором с момента загрузки страницы (иначе — сообщение
«Товар изменили…» и предложение загрузить актуальную версию; ничего не записывается).

### Счётчики и фильтр видимости

Над списком — сводка:

- **Всего товаров** — все документы коллекции, включая скрытые и повреждённые;
- **На витрине** — корректные товары с `hidden == false`, их видят покупатели;
- **Скрытых** — корректные товары с `hidden: true`;
- **Повреждённых документов** — документы, которые не проходят проверку формата (показывается,
  только если такие есть). Витрина их не показывает; откройте документ и исправьте поля.

Фильтр **«Видимость»**: «Все товары», «На витрине», «Скрытые». Он сочетается с поиском и другими
фильтрами и хранится в адресе страницы (`?visibility=visible` или `?visibility=hidden`), поэтому
сохраняется после возврата из формы товара. Счётчики всегда считают всю коллекцию, а не результат фильтра.

### Как скрыть товар

Скрытый товар не показывается покупателям в каталоге, но **не удаляется**: все данные остаются
в Firestore, и товар можно вернуть в любой момент.

- **В списке:** кнопка **«Скрыть»** в строке товара.
- **На странице товара:** блок **«Видимость на витрине»** → **«Скрыть с витрины»**.

Меняются только поля `hidden` и `updatedAt` — остальные данные товара и заказы не затрагиваются.
На странице товара кнопка недоступна, пока в форме есть несохранённые изменения: сначала сохраните
или отмените их. Сохранение формы видимость не меняет.

**Последний товар на витрине скрыть нельзя.** Если бы на витрине не осталось видимых товаров,
покупатели увидели бы резервный демо-каталог вместо вашего. Кнопка «Скрыть» у последнего видимого
товара заблокирована с объяснением; сервер повторно проверяет это в транзакции (на случай, если
другой товар одновременно скрыли в другой вкладке).

Повреждённому документу изменить видимость нельзя — сначала исправьте его в форме и сохраните.

### Как вернуть товар на витрину

- **В списке:** кнопка **«Показать»** в строке скрытого товара (удобно с фильтром «Скрытые»).
- **На странице товара:** блок «Видимость на витрине» → **«Показать на витрине»**.

Товар сразу снова доступен покупателям — с теми же данными, ценами и адресом `/product/{id}`.

### Как окончательно удалить товар

Удаление — только со страницы товара и только для **скрытого** товара («сначала скрыть, потом удалить»):
так удаление не меняет витрину, а у видимого товара кнопка удаления заблокирована.
Это ограничение проверяют и интерфейс, и Firestore Rules: запрос на удаление видимого товара
сервер отклонит, даже если отправить его в обход админ-панели. Повреждённый документ без поля
`hidden` сначала исправьте в форме и скройте — только после этого его можно удалить.

1. Скройте товар (см. выше).
2. Внизу страницы товара, в блоке **«Удаление товара»**, нажмите **«Удалить товар…»**.
3. В окне проверьте название, бренд и ID товара.
4. Нажмите **«Скачать JSON-копию»** — без этого кнопка удаления не включится.
5. Введите ID товара точно так, как он указан (с учётом регистра).
6. Нажмите **«Удалить навсегда»**. После удаления откроется список товаров, счётчики пересчитаются.

Окно можно закрыть кнопкой «Отмена», клавишей Escape или щелчком по фону (кроме момента удаления).
Фокус при открытии стоит на «Отмене», Tab переходит по элементам только внутри окна.

### Зачем нужна JSON-копия

Удаление **необратимо**: в Firestore нет корзины, документ удаляется сразу. Файл
`product-<id>-<ГГГГ-ММ-ДД>.json` содержит документ целиком (все поля, `updatedAt` — строкой ISO)
в поле `document`. По нему товар можно восстановить вручную: создать документ `products/<id>`
с теми же полями (в Firebase Console или через форму «Новый товар» с тем же ID). Храните копию,
пока не уверены, что товар больше не нужен.

### Ограничения при удалении

- Удалить можно только скрытый товар. Если его вернули на витрину в другой вкладке — удаление
  отменяется («Товар снова показывается на витрине»), ничего не удаляется.
- Если товар изменили после открытия страницы — удаление отменяется, предлагается загрузить
  актуальную версию.
- Если на витрине сейчас нет ни одного видимого товара, удаление отменяется: сначала покажите хотя бы
  один товар, иначе витрина закрепилась бы на демо-каталоге.
- Несохранённые изменения формы удаляемого товара теряются (окно предупреждает об этом).
- Удаляется только документ `products/{id}`. Файл изображения в `public/images/products` не удаляется.

### Что происходит с заказами, корзинами и избранным

- **История заказов не меняется.** В каждом заказе хранится копия позиции (название, бренд, объём,
  цена), поэтому заказы с удалённым или скрытым товаром по-прежнему открываются у покупателя
  и в разделе «Заказы» с исходными данными. Данные покупателей тоже не меняются.
- Корзина и избранное хранятся в браузере покупателя. Когда покупатель открывает сайт, товары,
  которых нет на витрине (скрытые или удалённые), убираются из его корзины и избранного. Это
  относится и к скрытию: если позже вернуть товар на витрину, в уже очищенную корзину он сам
  не вернётся — покупатель добавит его заново.
- **Проверка перед оформлением заказа.** Если покупатель держит страницу оформления открытой,
  пока товар скрывают, удаляют или меняют, заказ по устаревшим данным не оформится: перед окном
  оплаты и ещё раз прямо перед сохранением каталог заново читается из Firestore.
  - Товар скрыт, удалён, нет в наличии или нет выбранного объёма — заказ не оформляется; покупатель
    видит список таких товаров и может удалить их из корзины, выбрать другой объём (другой объём сам
    не подставляется) или вернуться в каталог.
  - Изменилась цена — покупатель видит старую и новую цену и пересчитанную сумму (со скидкой и
    доставкой) и подтверждает заказ ещё раз. При оплате картой окно оплаты открывается заново.
  - Если каталог не удалось прочитать или витрина переключилась на резервный демо-каталог, заказ
    не оформляется — покупатель видит ошибку и повторяет попытку.
  - В заказ попадают название, бренд, объём и цена из этой свежей проверки; структура заказа прежняя.

### Демо-каталог не подменяет ваш каталог

Витрина показывает резервный демо-каталог только если в коллекции нет ни одного видимого товара.
Скрытие и удаление через админ-панель всегда оставляют на витрине хотя бы один видимый корректный
товар, поэтому после этих действий покупатели продолжают видеть каталог из Firestore. Где сейчас
берётся каталог, видно в строке **«Витрина сейчас»** в разделе «Товары».

## 8. Модерация отзывов — этап A (переходный)

Готовится премодерация отзывов: новый отзыв получит статус `pending` и появится на сайте только после
одобрения администратором (`approved`); отклонённый (`rejected`) администратор сможет удалить навсегда.
Отзывы по-прежнему оставляют все посетители без регистрации. Этап A только готовит базу —
**поведение сайта не меняется**: отзывы публикуются сразу, как и раньше, а интерфейса модерации пока нет.

### Что изменилось в правилах

- В `isValidReview` разрешено поле `status`. Оно **необязательное**: старая версия сайта (уже открытая
  у посетителей) отправляет отзыв без `status`, и он принимается, как раньше.
- Если `status` передан, допустимо только `'pending'`. Отправить из браузера отзыв сразу со статусом
  `approved` или `rejected` нельзя.
- Остальные проверки отзыва не менялись (поля, длины, оценка 1–5, `lang`, `createdAt == request.time`).
- Чтение по-прежнему публичное и **без фильтра по статусу**; изменять и удалять отзывы из браузера
  по-прежнему нельзя никому, включая администратора.
- Правила `users`, `orders`, `admins` и `products` не менялись.

### Индекс

Для будущего запроса витрины `where('status', '==', 'approved')` + `orderBy('createdAt', 'desc')`
нужен составной индекс коллекции `reviews`: `status` (по возрастанию) + `createdAt` (по убыванию).
Он описан в `firestore.indexes.json` (`indexes`). Индекс строится несколько минут, поэтому его
создают заранее, до перехода сайта на фильтр по статусу. Создать его можно одним из способов:

- Firebase Console → Firestore → Indexes → **Composite** → Create index: коллекция `reviews`,
  поля `status` Ascending и `createdAt` Descending, область **Collection**;
- или `npx firebase-tools deploy --only firestore:indexes` — с учётом предупреждения из раздела 1
  (индексы, которых нет в файле, CLI предложит удалить — отвечайте «нет»).

Пока сайт не использует этот индекс, его наличие или отсутствие ни на что не влияет.

### Старые отзывы

У существующих отзывов поля `status` нет. На этапе A они **не меняются** и продолжают показываться
на сайте. Перед тем как витрина начнёт показывать только `approved`, им нужно один раз проставить
`status: 'approved'` (этап B, миграция) — иначе они пропадут с сайта.

### Порядок следующих этапов

1. **A** (этот): индекс + правило, принимающее отзывы и без `status`, и с `status: 'pending'`.
2. **B**: резервная копия и миграция старых отзывов в `status: 'approved'`.
3. **C**: сайт отправляет `status: 'pending'`, показывает и считает среднюю оценку только по `approved`,
   сообщает «отзыв отправлен на модерацию».
4. **D**: строгие правила — `status` обязателен, посетитель читает только `approved`, администратор
   читает все отзывы, меняет статус и удаляет отклонённые.
5. **E**: раздел «Отзывы» в админ-панели.

Правила этапа A можно публиковать в любой момент: они совместимы и с текущим сайтом, и со следующей
версией, которая начнёт отправлять `status: 'pending'`.

## 9. Модерация отзывов — этап C (сайт)

Этапы A и B завершены: индекс `status + createdAt` создан, правила этапа A опубликованы, двум старым
отзывам вручную проставлен `status: 'approved'` (резервная копия до миграции — вне репозитория).

Что делает сайт теперь:

- **Новый отзыв** сохраняется с полями `name, rating, text, lang, status: 'pending', createdAt`.
  Вход не нужен — отзыв по-прежнему может оставить гость. После отправки форма очищается и показывает
  «Спасибо! Ваш отзыв отправлен на модерацию и появится после одобрения»; в список на странице отзыв
  не добавляется, средняя оценка не меняется.
- **Страница `/reviews` и блок на главной** запрашивают `where('status', '==', 'approved')` +
  `orderBy('createdAt', 'desc')` (индекс `status + createdAt`). Отзывы `pending`, `rejected` и документы
  без `status` посетители не видят.
- **Число отзывов и средняя оценка** (страница `/reviews` и карточка «Отзывы» на дашборде) считаются
  только по одобренным.

### Индексы отзывов

Оба составных индекса коллекции `reviews` описаны в `firestore.indexes.json`, опубликованы
(`npx firebase-tools deploy --only firestore:indexes --project aroma-donna`) и имеют статус **READY**
(в Console — Enabled):

| Индекс | Для чего |
|---|---|
| `status` по возрастанию + `createdAt` по убыванию | список одобренных отзывов: `where(status)` + `orderBy(createdAt desc)` |
| `status` по возрастанию + `rating` по возрастанию | число и средняя оценка одобренных: `where(status)` + `count()` + `average(rating)` |

Число отзывов и средняя оценка считаются **на сервере** (`getAggregateFromServer`).
В Console и в выводе `npx firebase-tools firestore:indexes` у этих индексов есть ещё поле `__name__` —
это ID документа, который Firestore сам добавляет последним в каждый составной индекс. В
`firestore.indexes.json` его указывать не нужно, и не стоит перезаписывать файл выводом этой команды.

Резервный расчёт в коде остаётся на случай, если индекс `status + rating` удалят или он ещё не построен
(например, в новом проекте Firebase): тогда Firestore отвечает `failed-precondition`, сайт читает
одобренные отзывы и усредняет оценки в браузере (в консоли — предупреждение `[reviews] Нет индекса…`).
Результат тот же, но каждый показ страницы `/reviews` читает все одобренные отзывы.

### Как одобрить или отклонить отзыв до появления раздела в админ-панели

Firebase Console → Firestore Database → `reviews` → документ → поле `status`: `approved` (показать
на сайте) или `rejected` (не показывать). Из браузера это сделать нельзя — правила запрещают изменять
отзывы до этапа D.

Правила и индексы на этапе C не менялись.

## 10. Модерация отзывов — этап D (строгие правила)

Правила `reviews` в `firestore.rules` подготовлены и проверены на эмуляторе. **В Firebase они ещё
не опубликованы** — порядок публикации ниже.

### Правила

```
match /reviews/{reviewId} {
  allow read: if isAdmin() || resource.data.status == 'approved';
  allow create: if isValidReview(request.resource.data);
  allow update: if isAdmin() && isValidReviewModeration();
  allow delete: if isAdmin() && resource.data.status == 'rejected';
}
```

- **Создание** (`isValidReview`): любой посетитель, вход не нужен. Поля `name, rating, text, status,
  createdAt` обязательны, `lang` — по желанию, других полей нет. `status` — только `'pending'`,
  `createdAt == request.time`. Поле `moderatedAt` при создании передать нельзя.
- **Чтение**: посетитель — только `approved`, в том числе по ID документа; `pending` и `rejected`
  он не видит, даже свой только что отправленный отзыв. Запрос посетителя обязан содержать
  `where('status', '==', 'approved')` — запрос без фильтра Firestore отклоняет целиком.
  Администратор читает все отзывы, с фильтром и без.
- **Изменение** (`isValidReviewModeration`): только администратор и только поля `status`
  (`pending`, `approved` или `rejected`) и `moderatedAt`, причём `moderatedAt == request.time`
  (`serverTimestamp()`). Имя, оценку, текст, язык и дату создания изменить нельзя.
- **Удаление**: только администратор и только отзыв, у которого сейчас `status == 'rejected'`
  (сначала отклонить, потом удалить).
- Гость, обычный покупатель и пользователь с анонимным входом отзывы не меняют и не удаляют.
- Администратор — по-прежнему тот, у кого есть документ `admins/{uid}` (`isAdmin()`).
- Правила `users`, `orders`, `admins`, `products` и запрет по умолчанию не менялись.

### Совместимость с сайтом

Все запросы сайта к `reviews` (`src/services/reviewsStore.js`) уже соответствуют правилам:
список и статистика — с фильтром `status == 'approved'`, новый отзыв — с `status: 'pending'`.
Карточка «Отзывы» на дашборде читает ту же статистику одобренных. Изменений в коде сайта и новых
индексов не требуется. Раздел модерации в админ-панели — следующий этап (E).

### Порядок публикации

1. Выложить сайт с изменениями этапов A–C (он отправляет `status: 'pending'` и фильтрует список).
   **Сайт без этих изменений с правилами этапа D не работает**: список отзывов получит
   `permission-denied`, а отправка отзывов будет отклоняться.
2. Убедиться на рабочем сайте, что форма показывает сообщение о модерации, а список отзывов загружается.
3. Опубликовать правила: `npx firebase-tools deploy --only firestore:rules --project aroma-donna`.
4. Посетители со старой открытой вкладкой увидят ошибку загрузки отзывов до перезагрузки страницы.

### Тесты правил на эмуляторе

`npm run test:rules` запускает `tests-emulator/firestore.rules.emulator.js` на локальном Firebase
Emulator в demo-проекте `demo-aroma-donna` (существует только локально — настоящая база `aroma-donna`
не используется). Нужна Java 21+ (проверено с Eclipse Temurin 21.0.13); эмулятор Firestore CLI
скачивает при первом запуске. Обычный `npm test` эмулятор не запускает.

Результат: **51 тест, 51 пройден**. Проверяется:

- гость, покупатель и анонимный пользователь: создание `pending` — да; `approved`, `rejected`, без
  `status`, с `moderatedAt`, с чужой датой, с неверной оценкой, длиной, языком или лишним полем — нет;
- они же: запрос `status == approved` + `orderBy(createdAt)` и статистика (`count`, `average`)
  возвращают только одобренные; `pending` и `rejected` не читаются даже по ID; запросы без фильтра
  отклоняются; изменить и удалить отзыв нельзя;
- администратор: читает все статусы; меняет `status` на `approved`, `rejected`, `pending` только вместе
  с `moderatedAt` = времени сервера; не может изменить другие поля, поставить неизвестный статус,
  своё время или удалить `status`; удаляет только `rejected`;
- `users`, `orders`, `products` (включая удаление только скрытого товара, этап 5c.8), `admins`
  и закрытые неописанные коллекции работают как раньше.

Тесты дополнительно проверены «мутациями»: если в правилах вернуть `read: if true`, правило создания
этапа A, `update: if isAdmin()` или `delete: if isAdmin()`, убрать проверку `moderatedAt` или
ограничение изменяемых полей, — соответствующие тесты падают.
