# AROMA DONNA — чек-лист запуска

Что нужно сделать вручную в Firebase Console и Vercel перед публикацией, и в каком порядке.
Код и тесты к этому готовы. Реальные Firebase, App Check, Telegram и Vercel
**в тестах не подключались** — всё проверено только на эмуляторах (`demo-aroma-donna`) с подменённым
Telegram. Поэтому каждый пункт ниже нужно один раз проверить на рабочем проекте.

> Секреты (ключ сервисного аккаунта, `ORDER_HMAC_SECRET`, токен Telegram)
> вводятся только в Firebase Console и Vercel → Environment Variables. Не пишите их в GitHub, чаты и письма.

## Как устроено оформление заказа (коротко)

- Заказ создаёт **только сервер**: функция Vercel `POST /api/order` (Firebase Admin SDK).
  Браузер присылает только товары, количество, способы доставки и оплаты, данные покупателя.
  Цены, итог, номер, дату и статусы считает сервер по каталогу Firestore.
- Вошедший покупатель подтверждается ID-токеном Firebase, гость — токеном **App Check (reCAPTCHA Enterprise)**.
- Правила Firestore запрещают создавать заказы из браузера (и обычные, и гостевые).
- Гостевые заказы лежат в `guests/{guestKey}/orders/{orderId}`; их видит и меняет (только статус) администратор.
- Уведомление о заказе отправляет сервер в Telegram; при сбое администратор повторяет отправку
  кнопкой в карточке заказа (`POST /api/order-notify`, только администратор).

## Порядок действий

### 1. Firebase Authentication

1. Authentication → Sign-in method: включены **Email/Password** и **Google** (см. [GOOGLE_AUTH.md](GOOGLE_AUTH.md)).
2. Authentication → Settings → **Authorized domains**: добавить рабочий домен и домен Vercel
   (`<проект>.vercel.app`). `localhost` оставить для разработки.
3. Authentication → Templates → **Password reset**: проверить язык письма и адрес отправителя.
   Вручную: запросить восстановление пароля на тестовый адрес и пройти по ссылке.

### 2. Владелец и администраторы

Подробно, с типами полей и проверкой — [ADMIN_SETUP.md](ADMIN_SETUP.md), раздел 2.
Для пункта 1 нужен сайт, подключённый к рабочему Firebase: уже опубликованный сайт или Preview-деплой
(шаг 7). Если сайта ещё нет, выполните этот шаг в начале шага 7 — до проверок админ-панели. Кратко:

1. Владелец регистрируется на сайте; его UID — Authentication → Users.
2. Firestore → `admins/{UID}` (Document ID — UID): `grantedAt` (timestamp), `grantedBy` (string, тот же UID),
   необязательно `label` (string). Если документ уже есть — не менять.
3. Firestore → `adminConfig/primary` — ровно пять полей:
   `ownerUid` (string, UID), `pendingOwnerUid` (**null**), `previousOwnerUid` (**null**),
   `updatedAt` (timestamp), `updatedBy` (string, UID). Тип null — не строка `"null"`.
4. Проверка: выйти и войти снова → `/admin` → в меню пункт «Администраторы», у владельца роль
   «Главный администратор».

Остальных администраторов назначает и снимает владелец в админ-панели (раздел «Администраторы»);
это защищено правилами Firestore, а не только интерфейсом.

### 3. Сервисный аккаунт (Firebase Admin SDK) — для `/api/order` и `/api/order-notify`

1. Firebase Console → Project settings → **Service accounts** → Generate new private key → JSON-файл.
2. Закодировать файл в одну строку base64 (macOS): `base64 -i ключ.json | tr -d '\n'`.
3. Значение → Vercel → `FIREBASE_SERVICE_ACCOUNT_B64` (см. шаг 6). JSON-файл после этого удалить
   с компьютера или хранить в надёжном месте; в проект его не класть.

Сервер проверяет файл: тип `service_account`, проект не `demo-*`. На Vercel режим эмулятора невозможен.

### 4. App Check и reCAPTCHA Enterprise (Google Cloud Fraud Defense) — для гостевых заказов

Сайт использует провайдер **reCAPTCHA Enterprise** (`ReCaptchaEnterpriseProvider`). Классический
reCAPTCHA v3 Firebase пометил устаревшим — его ключи (пара «site key + secret key» из
google.com/recaptcha/admin) **не подходят** и никуда не вводятся.

1. Google Cloud Console → проект `aroma-donna` → **Security → Fraud Defense** (бывший reCAPTCHA Enterprise).
   Если предложено — включить **reCAPTCHA Enterprise API**.
2. **Create key**: тип **Web**; домены — рабочий домен и `<проект>.vercel.app` (без `https://`);
   **`localhost` не добавлять**; «Use checkbox challenge» **не включать** (App Check нужен ключ по оценке).
   Получится один ключ (идентификатор) — отдельного секретного ключа в этой схеме нет.
3. Firebase Console → **App Check** → Apps → веб-приложение → **reCAPTCHA Enterprise** → вставить этот ключ.
   TTL — по умолчанию (1 час), порог риска — по умолчанию (0.5) → Save.
4. Тот же ключ → Vercel → `VITE_RECAPTCHA_SITE_KEY` (Production и Preview) → новый деплой.
5. **Важно:** в App Check → APIs **не включать Enforcement** для Cloud Firestore и Authentication.
   Сайт отправляет токен App Check только при гостевом оформлении (на наш сервер), а не в каждом запросе
   к Firestore — включённое Enforcement сломает каталог, вход и кабинет. Защиту гостевых заказов
   обеспечивает сервер: он проверяет одноразовый токен (`verifyToken` с `consume: true`, повтор токена отклоняется).

Стоимость: каждый токен App Check — проверка reCAPTCHA (assessment), платная сверх бесплатной квоты
Fraud Defense. Автообновление токенов в коде выключено, поэтому проверки создаются только при оформлении
гостевого заказа (одноразовый токен и, после подключения App Check, обычный токен для запросов Firebase
на этой странице — не чаще раза в час). Квоту и цены проверьте в Google Cloud перед запуском.

Без `VITE_RECAPTCHA_SITE_KEY` гость увидит сообщение «не удалось подтвердить…» и не сможет оформить заказ;
вошедший покупатель — сможет. То же сообщение будет, если ввести ключ классического reCAPTCHA v3
или ключ с режимом «checkbox».

### 5. Telegram

Те же `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`, что и для формы «Контакты» (README, раздел 9).
Сбой Telegram не отменяет заказ: статус уведомления «Не отправлено», повтор — кнопкой в админке.
Автоматических повторов нет.

### 6. Vercel → Settings → Environment Variables (Production и Preview)

| Переменная | Где взять | Секрет |
|---|---|---|
| `VITE_FIREBASE_API_KEY`, `_AUTH_DOMAIN`, `_PROJECT_ID`, `_STORAGE_BUCKET`, `_MESSAGING_SENDER_ID`, `_APP_ID` | Firebase → Project settings → Web app | нет (публичные) |
| `VITE_EMAILJS_SERVICE_ID`, `_TEMPLATE_ID`, `_PUBLIC_KEY` | EmailJS | нет (публичные) |
| `VITE_RECAPTCHA_SITE_KEY` | ключ reCAPTCHA Enterprise (Fraud Defense), тип Web | нет (публичный) |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` | @BotFather, чат | **да** |
| `FIREBASE_SERVICE_ACCOUNT_B64` | шаг 3 | **да** |
| `ORDER_HMAC_SECRET` | `openssl rand -hex 32` (не короче 32 символов) | **да** |

**Не задавать на Vercel:** `VITE_USE_EMULATORS`, `FIRESTORE_EMULATOR_HOST`, `FIREBASE_AUTH_EMULATOR_HOST`,
`APP_CHECK_TEST_SECRET` — они только для тестов. Если `ORDER_HMAC_SECRET` поменять позже, защита от
повторных заказов и счётчики лимитов начнутся заново (старые заказы не пострадают).

После изменения переменных — новый деплой (Vercel подставляет `VITE_*` при сборке).

### 7. Preview-деплой и проверка — со СТАРЫМИ правилами Firestore

На этом шаге новые правила ещё **не опубликованы**. Новая версия сайта с ними совместима, кроме одного:
**смена статуса гостевого заказа в админке** до публикации правил не работает — в старых правилах нет
разрешения на запись в `guests/{guestKey}/orders`, и админка покажет «нет прав…» (документ не меняется).
Это ожидаемо; проверяется на шаге 10.

Preview работает с **рабочей** базой Firebase (отдельного тестового проекта нет): тестовые аккаунты
и заказы — настоящие записи. Для Preview лучше задать отдельный тестовый `TELEGRAM_CHAT_ID`,
а тестовые заказы потом перевести в статус «Отменён» (удалять заказы правила не дают).
Google-вход на Preview работает, только если его адрес добавлен в Authorized domains.

Проверить на Preview:

1. Регистрация, вход по e-mail и через Google, выход, восстановление пароля.
2. Каталог, поиск и фильтры, карточка товара, корзина, избранное.
3. Гостевой заказ (наличные и «карта DEMO»): номер заказа на экране, корзина очищена,
   сообщение пришло в Telegram, заказ виден в админке с меткой «Гость».
4. Заказ вошедшего покупателя: виден в кабинете и в админке.
5. Двойное нажатие «Оформить» — один заказ.
6. Админка: смена статуса **обычного** заказа (покупателя с аккаунтом) — работает.
   «Администраторы» — только у владельца.
7. Временно задать неверный `TELEGRAM_CHAT_ID` на Preview → заказ сохраняется со статусом уведомления
   «Не отправлено» → вернуть правильное значение и передеплоить Preview → «Отправить повторно» в карточке заказа.
8. Форма «Контакты» (EmailJS и Telegram), отзыв (появляется после одобрения в админке).
9. Языки RU / KG / EN, светлая и тёмная темы, телефон и компьютер.

**Не проверять на этом шаге:** смену статуса гостевого заказа (шаг 10).
Если что-то из списка не работает — не переходить к шагу 8.

### 8. Индексы Firestore — сверка (обязательно до публикации)

Публикация индексов приводит Firebase к содержимому `firestore.indexes.json`; индексы, которых нет в файле,
Firebase CLI предлагает **удалить**. Поэтому:

1. Вывести индексы рабочего проекта (только чтение): `npx firebase-tools firestore:indexes --project <рабочий-проект>`.
2. Сравнить с `firestore.indexes.json`. Поле `__name__` в составных индексах Firestore добавляет сам — не расхождение.
3. **Есть расхождения или в Console есть дополнительные индексы — остановиться, индексы не публиковать
   и сообщить об этом.** Существующие индексы без отдельного согласования не удалять.
4. Расхождений нет — опубликовать **только индексы**, без `--force`:
   `npx firebase-tools deploy --only firestore:indexes --project <рабочий-проект>`.
   Если CLI спросит об удалении индексов — ответить «нет» и вернуться к пункту 3.

Публикацию индексов можно отложить: без нового индекса `orders.createdAt` (Collection group) список заказов
в админке сортируется в браузере. **Удалять существующие индексы нельзя**: составные индексы отзывов уже
опубликованы в рабочем проекте (ADMIN_SETUP.md, раздел 9), и без индекса `status + createdAt` страница
`/reviews` и отзывы на главной не загрузятся — резервного варианта для этого запроса нет.
Правила откладывать нельзя.

### 9. Правила Firestore и Production-деплой

1. Опубликовать **только правила** (отдельно от индексов):
   `npx firebase-tools deploy --only firestore:rules --project <рабочий-проект>`
   (или скопировать `firestore.rules` в Console → Firestore Database → Rules → Publish).
2. **Сразу после этого** — Production-деплой новой версии сайта на Vercel.

Почему такой порядок:

- новые правила запрещают создавать заказы из браузера. Если на рабочем домене ещё старая версия сайта
  (она создавала заказ напрямую в Firestore), после публикации правил оформление в ней перестанет работать —
  поэтому Production-деплой идёт сразу за правилами;
- до публикации правил новая версия сайта работает, но администратор не может менять статус гостевых заказов,
  а покупатель технически может записать заказ в Firestore в обход сервера — поэтому правила не откладываются.

### 10. Проверка после публикации правил (рабочий домен)

1. Админка → карточка гостевого заказа (метка «Гость») → смена статуса — сохраняется, сообщения «нет прав…» нет.
   То же — под обычным администратором, если он есть.
2. Гостевой заказ и заказ вошедшего покупателя на рабочем домене — оформляются; сообщение в Telegram пришло.
3. Вход, регистрация, каталог, кабинет — работают.
4. Тестовые заказы — перевести в статус «Отменён».

### 11. EmailJS

EmailJS → Account → Security: разрешить только рабочий домен (и домен Vercel), включить лимиты.

## Что уже проверено автоматически (эмуляторы, без реальных сервисов)

- В клиентской сборке нет секретов: ни ключа сервисного аккаунта, ни `ORDER_HMAC_SECRET`, ни токена Telegram,
  ни кода Admin SDK.
- Правила по ролям: посетитель, покупатель, владелец, обычный администратор, отозванный администратор, гость
  (`tests-emulator/securityRoles.emulator.js`, `tests-emulator/firestore.rules.emulator.js`).
